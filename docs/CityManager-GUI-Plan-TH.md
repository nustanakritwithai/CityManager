# แผนปรับปรุง GUI ของ CityManager ตามภาพอ้างอิง

## 1 เป้าหมายและขอบเขต

ปรับหน้าตา CityManager ให้มีโครงสร้างอ่านง่ายแบบเกมสร้างเมืองในภาพที่ส่งมา โดยเก็บพื้นที่เมืองเป็นจุดหลัก แยกข้อมูลภาพรวมออกจากรายละเอียดอาคาร และเปิดข้อมูลเศรษฐกิจเชิงลึกได้โดยไม่ทำให้ผู้เล่นหลงทาง แนวทางคือใช้ภาพบ้านเป็นต้นแบบของการเลือกอาคาร และใช้ภาพ City stats เป็นต้นแบบของแดชบอร์ดเมือง ไม่คัดลอกภาพทั้งหมดหรือสร้างค่าจำลองขึ้นมาให้หน้าจอดูเต็ม

เอกสารนี้เป็นแผนออกแบบ ยังไม่ใช่การแก้โปรแกรมหรือข้อรับรองว่าฟังก์ชันทั้งหมดมีแล้ว ฐานอ้างอิงโครงการคือ [CityManager](https://github.com/nustanakritwithai/CityManager) ที่ main รุ่น 737653b6 ตามสถานะที่ใช้จัดทำแผน เกมเป็น PlayCanvas บนเว็บ แผนที่ 24 × 24 ช่อง มีครัวเรือน การทำงาน เงินสด การซื้อสินค้า บริษัท คนงาน สินค้าคงคลัง เงินกันไว้จ่ายค่าจ้าง กำไรประจำเดือน เงินคลัง บันทึกเหตุการณ์ โซน RCI ถนน และบันทึก/โหลดเกม

งานเมนูย่อย 5 หน้า ได้แก่ เงิน สินค้า กระเป๋าเงิน วิธีเล่น และสมมติฐาน พร้อมปุ่มย้อนกลับรายหน้า เป็นฐานที่ต้องรักษา แผนนี้เสนอให้จัดสิ่งเหล่านั้นเข้าสู่ระบบนำทางเดียวกัน ไม่รื้อทำใหม่และไม่เปลี่ยนกติกาเศรษฐกิจพร้อมกับเปลี่ยน GUI ก่อนเริ่มพัฒนาแต่ละระยะให้ตรวจสัญญาข้อมูลกับโค้ดจริงอีกครั้ง โดยชื่อฟิลด์ในเอกสารนี้เป็นชื่อเชิงออกแบบ เว้นแต่ระบุชัดว่าเป็นข้อมูลเดิม

## 2 สิ่งที่นำมาจากแต่ละภาพ

### ภาพบ้านและผู้อยู่อาศัย

ภาพแรกมีเมืองเป็นพื้นหลัง แถบทรัพยากรด้านบน ตัวควบคุมเวลาบริเวณบนซ้าย แผง House I ทางขวา และปุ่มกลมด้านล่าง แผงบ้านเริ่มด้วยชื่ออาคาร ตามด้วยจำนวนผู้พักอาศัยต่อความจุ และรายชื่อที่มีอาชีพเป็นแถว โครงสร้างนี้ดีเพราะตอบได้ทันทีว่าเลือกอะไร อยู่ที่ไหน และมีใครเกี่ยวข้อง

นำมาใช้กับ CityManager ดังนี้

- คงชื่ออาคารหรือชนิดช่องไว้หัวแผง พร้อมพิกัดและปุ่มเลื่อนกล้องไปยังตำแหน่งนั้น
- ใช้รายการครัวเรือนหรือคนงานที่มีความสัมพันธ์จริงกับอาคาร แทนรายชื่อคนที่แต่งขึ้น
- เปลี่ยนตัวเลขแบบ 8/10 เป็นจำนวนครัวเรือนที่เชื่อมกับอาคาร หากระบบไม่มีความจุ ไม่แสดงตัวหาร ไม่สร้างแถวว่าง VACANT ให้ดูเหมือนมีห้องพักจริง
- หนึ่งครัวเรือนไม่เท่ากับหนึ่งประชากร ห้ามเปลี่ยนจำนวน households ไปติดป้ายว่า “ประชากร” หรือ “คน” หากไม่มีแบบจำลองรายบุคคล
- ไม่สร้างชื่อ อายุ เพศ สุขภาพ หรืออาชีพละเอียดจากภาพ หากมีเพียงรหัสครัวเรือน ให้แสดง “ครัวเรือน #รหัส” และสถานะงานที่ระบบเก็บจริง
- ใช้พื้นผิวและกรอบที่มีลำดับชั้นชัด แต่ไม่ลอกภาพไม้ ตรา หรือไอคอนจากเกมต้นฉบับ

ตัวเลข 3/4 และจุดเปลี่ยนภาพที่ทับอยู่บนภาพแรกไม่ถือเป็นองค์ประกอบที่ต้องใส่ในเกม เพราะอาจเป็นตัวควบคุมของชุดภาพ ไม่ใช่ GUI ต้นฉบับ

### ภาพ City stats

ภาพที่สองแสดงหน้าต่างสถิติขนาดใหญ่ โปร่งแสง แบ่งเป็นบริการทางซ้าย ตารางจำนวนอาคาร คอลัมน์ประชากร แรงงานและค่าจ้างตรงกลาง และรายการทรัพยากรที่เลื่อนได้ทางขวา ด้านล่างยังเห็นแถบเครื่องมือเมือง

นำลำดับข้อมูลมาใช้ แต่ไม่บังคับให้เกมมีทุกระบบเหมือนภาพ

- แถบบริการเปลี่ยนเป็น “สถานะเมือง” ที่มีข้อมูลจริง เช่น เงินคลัง ครัวเรือน บริษัท สินค้าคงคลัง และงาน
- ตารางอาคารแยก R/C/I และถนนตามข้อมูลที่มี ไม่ใส่ขนาด 1×1 ถึง 4×4 หากเกมยังไม่มีขนาดอาคารหลายแบบ
- ประชากร แรงงาน และค่าจ้างเปลี่ยนเป็น “ครัวเรือนและการทำงาน” พร้อมนิยามหน่วยที่ตรงกับแบบจำลอง
- ทรัพยากรหลายรายการย่อเป็นสินค้าชนิดเดียวของเกม ไม่ใส่เหล็ก ไม้ อาหาร หรือแร่ต่างชนิดเพื่อเติมช่อง
- ไม่แสดงเกจน้ำ ไฟ โรงเรียน โรงพยาบาล หรือมลพิษเป็น 0 เพราะศูนย์สื่อว่าระบบทำงานแต่ไม่มีทรัพยากร ให้ซ่อนจากหน้าหลัก หรือระบุ “ยังไม่มีระบบนี้” ในหน้าขอบเขตการจำลอง
- ลดความโปร่งแสงของหน้าต่างลงเพื่อให้ตัวอักษรไม่จมหายกับเมือง โดยยังคงความรู้สึกว่าเป็นแผงซ้อนบนโลกเกม

## 3 โครงสร้างหน้าจอหลักสี่ชั้น

### ชั้นที่หนึ่ง แถบข้อมูลด้านบน

ซ้ายเป็นชื่อเมืองหรือชื่อเกมและช่วงเวลาของเกม กลางเป็นเงินคลัง จำนวนครัวเรือน จำนวนงานที่มีข้อมูลจริง และสินค้าคงคลังรวม ขวาเป็นปุ่มสถิติเมือง บันทึก/โหลด และเมนูเพิ่มเติม ทุกค่ามีหน่วยกำกับ เช่น “เงินคลัง 12,000 หน่วยเงิน” ไม่สมมติว่าเป็นบาทหรือดอลลาร์

แสดงเพียง 3 ถึง 4 ตัวชี้วัดหลักบนจอใหญ่ ตัวชี้วัดที่เหลือเปิดในแดชบอร์ดได้ แตะเงินคลังไปหน้าเงิน แตะสินค้าไปหน้าสินค้า และแตะครัวเรือนไปหมวดครัวเรือน การแตะตัวเลขต้องมีผลเหมือนการแตะป้าย ไม่ทำให้มีพื้นที่กดแคบเฉพาะไอคอน

ตัวควบคุมหยุด/เดินเวลาต้องสะท้อนสถานะจริง หากเกมมีเพียงหยุดและเดิน ไม่ใส่ความเร็ว 2× หรือ 4× ที่ยังใช้ไม่ได้ ระบุ “กำลังเดินเวลา” หรือ “หยุดชั่วคราว” เป็นข้อความด้วย การเปิดหน้าข้อมูลไม่เปลี่ยนความเร็วเองโดยเงียบ และไม่ยืมสถานะ GAME PAUSED จากภาพมาเป็นข้อเท็จจริงของเกม

### ชั้นที่สอง พื้นที่เมืองและเครื่องมือด้านล่าง

พื้นที่เมืองต้องยังเห็นจุดเลือกและกรอบอาคาร แม้เปิดแผงด้านข้าง วางแถบคำสั่งล่างเป็นกลุ่ม “ตรวจสอบ” “ถนน” “ที่อยู่อาศัย R” “พาณิชย์ C” “อุตสาหกรรม I” และคำสั่งอื่นที่เกมรองรับจริง ปุ่มสถิติและคู่มือไม่ปะปนกับเครื่องมือก่อสร้าง

เลือกเครื่องมือแล้วแสดงชื่อ โหมด และวิธียกเลิกเหนือแถบล่าง ถ้ามีต้นทุนที่ engine ระบุ ให้แสดงก่อนวาง ไม่คิดราคาเองจากจำนวนช่องหากยังไม่มีสัญญาราคานั้น การลากถนนหรือโซนแสดงตัวอย่างพื้นที่ โดยผลลัพธ์ที่เกิดจริงยังเป็นหน้าที่ของ simulation command เดิม

ปุ่มที่เลือกใช้ทั้งกรอบ สี และข้อความ “เลือกอยู่” ไม่ใช้สีเพียงอย่างเดียว กด Escape หรือปุ่ม “ยกเลิกเครื่องมือ” กลับโหมดตรวจสอบ การกดบนแผงต้องไม่ทะลุไปวางถนนหรืออาคารบนแผนที่ คำสั่งรื้อถ้ารองรับต้องแยกจากการตรวจดูและแสดงผลกระทบที่ยืนยันได้ ไม่เสนอ undo หาก engine ยังย้อนสถานะไม่ได้

### ชั้นที่สาม แผงตรวจรายละเอียดตามสิ่งที่เลือก

บนเดสก์ท็อปใช้แผงขวากว้างเป้าหมาย 320 ถึง 380 CSS pixels มีหัวแผงติดอยู่ขณะเลื่อน ส่วนเนื้อหาเลื่อนเองได้ ปุ่มปิดเข้าถึงง่าย ค่าที่เปลี่ยนระหว่างเดินเกมมีเวลาหรือ tick อ้างอิง การเปลี่ยนสิ่งที่เลือกต้องอัปเดตข้อมูลทั้งแผงใน snapshot เดียว ป้องกันชื่ออาคารเก่าปนกับยอดเงินใหม่

หากสิ่งที่เลือกถูกลบหรือไม่อยู่ในสถานะเกมหลังโหลด ให้แจ้ง “รายการนี้ไม่อยู่ในเมืองแล้ว” แล้วกลับสู่หน้าตรวจสอบว่าง ไม่แสดงข้อมูลเดิมค้าง และไม่ทำให้หน้าต่างพัง

### ชั้นที่สี่ แดชบอร์ดสถิติเมือง

เปิดเป็นหน้าต่างใหญ่ที่อ่านรายละเอียดได้ ใช้ชื่อ “สถิติเมือง” พร้อมปุ่มปิด ช่วงเวลา และคำอธิบายสั้นว่าเป็นค่าปัจจุบันหรือผลของเดือนที่ปิดแล้ว บนจอใหญ่ให้เห็น 3 คอลัมน์หลักพร้อมกัน ได้แก่ สถานะเมือง โครงสร้างเมืองและครัวเรือน และเศรษฐกิจสินค้า โดยมีแท็บลงรายละเอียด แทนการอัดทุกคอลัมน์เหมือนภาพจนเล็กเกินอ่าน

เมื่อเปิดแดชบอร์ดให้ปิดแผงตรวจอาคารชั่วคราว แต่จำรายการที่เลือกไว้ ปิดแดชบอร์ดแล้วคืนแผงเดิมและกล้องเดิม ห้ามให้มีหน้าต่างข้อมูลซ้อนหลายชั้นจนไม่รู้ว่าปุ่มย้อนกลับจะไปไหน

## 4 รายละเอียดแผงตรวจอาคาร

### บ้านหรือโซนที่อยู่อาศัย

หัวแผงมีชนิด พิกัด และสถานะที่ระบบระบุจริง ถ้าช่องเป็นโซนเปล่าให้ใช้คำว่า “โซนที่อยู่อาศัย” ไม่เรียกว่า “บ้านที่มีผู้อยู่อาศัย” ส่วนสรุปแสดงจำนวนครัวเรือนที่เชื่อมกับสิ่งนี้ โดยนับความสัมพันธ์จริง ไม่ใช้จำนวน tile ของโซนแทนจำนวนบ้าน

รายการครัวเรือนแต่ละแถวประกอบด้วยรหัส เงินสด สถานะงาน และข้อมูลการซื้อที่มีการบันทึก พร้อมเปิดรายละเอียดเฉพาะครัวเรือนได้ หากข้อมูลไม่มีตัวแทนบุคคล ให้ใช้ไอคอนบ้านหรือกลุ่ม ไม่ใช้ภาพใบหน้าบุคคลเพื่อชวนเข้าใจว่ามีประชากรรายคน

หน้ารายละเอียดครัวเรือนแยก “ยอดเงินสดตอนนี้” “งานปัจจุบัน” และ “การซื้อในช่วงที่บันทึก” ชัดเจน มีปุ่มไปบริษัทที่ทำงานเมื่อมีรหัสบริษัทที่ยังใช้งานได้ หากไม่มีงานจริงใช้ “ไม่มีงานที่เชื่อมอยู่” ส่วน “ว่างงาน” ใช้ได้ต่อเมื่อ engine นิยามครัวเรือนนั้นว่าเป็นแรงงานที่พร้อมทำงาน

### บริษัทหรืออาคารเศรษฐกิจ

หัวแผงแสดงชนิดและรหัสบริษัท ตามด้วยคนงาน สินค้าคงคลัง เงินสด เงินกันไว้จ่ายค่าจ้าง และกำไรของงวดที่ระบุจริง แยกค่าที่เป็นยอดคงเหลือออกจากผลดำเนินงานด้วยหัวหมวดย่อย ไม่ใช้กำไรแทนยอดเงินสด

รายชื่อคนงานต้องอิงรายการอ้างอิงจากบริษัทไปครัวเรือนจริง ห้ามอนุมานว่า “จ้างงานเต็ม” จากจำนวนคนงานอย่างเดียว หากไม่มีตำแหน่งงานสูงสุด การแสดงคนงานปัจจุบัน/ความจุทำได้เมื่อมีความจุจริงและรู้ว่าค่านี้เป็นคน งาน หรือครัวเรือน

ถ้ามีเหตุขัดข้องที่ engine บันทึก เช่น จ่ายค่าจ้างไม่ได้หรือสินค้าหมด ให้แสดงเหตุการณ์พร้อมช่วงเวลา แต่ไม่วินิจฉัยสาเหตุจากยอดเงินต่ำเพียงค่าเดียว ปุ่ม “ดูเงิน” และ “ดูสินค้า” เชื่อมกับสองเมนูเดิมพร้อมตัวกรองบริษัท โดยถ้าตัวกรองยังไม่รองรับ ให้เปิดหน้าปกติพร้อมหัวข้อบริษัท ไม่แอบสร้างพฤติกรรมใหม่ที่ไม่มีสัญญารองรับ

### ถนนและพื้นที่ว่าง

ถนนแสดงชนิด พิกัด และข้อมูลที่มีจริง ไม่แสดงรถต่อชั่วโมง ความแออัดหรือเวลาเดินทางหากยังไม่มีระบบจราจร พื้นที่ว่างแสดงพิกัดและเครื่องมือที่เลือกอยู่ พร้อมคำแนะนำการวางโซนแบบสั้น ข้อมูลเครือข่ายการเข้าถึงถนนต้องตรวจว่ามีผลคำนวณจริงก่อนใช้คำว่า “เชื่อมต่อแล้ว”

## 5 รายละเอียดสถิติเมืองและเมนูเดิม

หน้าภาพรวมใช้กลุ่มข้อมูลต่อไปนี้ โดยการ์ดแต่ละใบมีชื่อ หน่วย ช่วงเวลา และลิงก์ลงรายละเอียด

1. สถานะเมือง: เงินคลัง ครัวเรือน บริษัท และจำนวนช่องถนนหรือโซน โดยบอกชัดว่าเป็นช่องหรืออาคาร
2. โครงสร้าง RCI: แถว R/C/I และถนน แยก “ช่องที่กำหนดโซน” จาก “อาคารหรือกิจการที่เกิดขึ้นจริง” ถ้าทั้งสองชุดมีข้อมูล ห้ามนำมารวมเป็นจำนวนเดียว
3. ครัวเรือนและงาน: ครัวเรือนทั้งหมด ครัวเรือนที่เชื่อมกับงาน และรายการที่ไม่เชื่อมกับงาน การหารอัตราการจ้างต้องมีนิยามฐานประชากรที่ถูกต้องก่อน
4. การเงิน: เงินคลังรวม ยอดเงินสดครัวเรือนรวม ยอดเงินสดบริษัทรวม และกำไรงวดล่าสุด แสดงคนละบรรทัด ไม่รวมทุกอย่างเป็น “รายได้เมือง”
5. สินค้า: สินค้าคงคลังรวม และปริมาณซื้อ ผลิต หรือขายเฉพาะรายการที่มีข้อมูลสะสมจริง ปริมาณคงคลังเป็น stock ณ เวลาใดเวลาหนึ่ง ส่วนผลิต/ขายเป็น flow ในช่วงเวลา ต้องแยกหน่วยและคำอธิบาย
6. บันทึกเหตุการณ์: เหตุการณ์ล่าสุด พร้อมปุ่มเปิดรายการทั้งหมด จัดกลุ่มความรุนแรงจากประเภทเหตุการณ์ที่มีจริง ไม่ใช้ข้อความสุ่มสร้างความตื่นเต้น

เมนูเงิน สินค้า กระเป๋าเงิน วิธีเล่น และสมมติฐานยังคงเป็นหน้าหลักของหมวดเดิม การปรับรอบแรกจำกัดที่ header, spacing, card, icon และเส้นทางนำทางร่วมกัน ปุ่ม “ย้อนกลับ” ทุกหน้าต้องกลับจุดที่เข้ามาจริง หากเข้าจากแดชบอร์ดให้กลับแดชบอร์ด หากเข้าจากแผงบริษัทให้กลับบริษัท ไม่บังคับกลับเมนูแรกทุกครั้ง

หน้าวิธีเล่นควรอธิบายวงจรที่เกมทำจริงเป็นลำดับงาน การได้รับเงิน การซื้อสินค้า และการดำเนินกิจการ หน้าสมมติฐานบอกข้อจำกัด เช่น สินค้าชนิดเดียว และครัวเรือนไม่ใช่ประชากรรายบุคคล ไม่ใช้หน้านี้เป็นข้อแก้ตัวให้ตัวเลขในหน้าหลักติดป้ายผิด

## 6 สัญญาข้อมูลและความถูกต้องของตัวเลข

ให้สร้างชั้นอ่านข้อมูลสำหรับ GUI ซึ่งคืน snapshot พร้อม simulation tick, period identifier, entity identifier และสถานะข้อมูล แต่ละ metric ต้องมี value, unit, period, source และ availability เป็นแนวทาง ไม่บังคับเปลี่ยนชื่อฟิลด์ใน engine ให้ตรงตามเอกสาร

แยกความพร้อมเป็นสามระดับ

- มีอยู่แล้ว: อ่านค่าจริงจาก simulation เช่น เงินสด สินค้าคงคลัง เงินคลัง และกำไรเดือนที่ engine เก็บ ใช้คำเรียกตามความหมายจริง
- คำนวณจากข้อมูลเดิมได้: รวมยอดจากชุดข้อมูลที่ชัดเจน เช่น ผลรวมเงินสดบริษัท โดยระบุชุดบริษัทที่นับและจังหวะ snapshot รวมถึงวิธีจัดการรายการถูกลบ
- ต้องเพิ่มระบบก่อน: ความจุบ้าน ประชากรรายบุคคล อายุ การศึกษา เครือข่ายน้ำไฟ บริการเมือง และสินค้าหลายชนิด ไม่แสดงเป็นฟีเจอร์ทำงานแล้ว

ค่าศูนย์หมายถึงมีข้อมูลและมีค่าเป็นศูนย์ ค่าที่ไม่ทราบใช้ “ไม่มีข้อมูล” ค่าที่ระบบไม่รองรับใช้ “ยังไม่มีระบบนี้” และข้อมูลเก่าที่ไม่ตรง snapshot ใช้ “ข้อมูลยังไม่อัปเดต” ไม่แปลง null, undefined หรือ NaN เป็นศูนย์โดยอัตโนมัติ

ประเด็นการเงินต้องตรวจเพิ่มก่อนเชื่อม UI

- เงินกันค่าจ้างอาจเป็นส่วนหนึ่งของเงินสดบริษัท ไม่ถือว่าเป็นเงินอีกก้อนและไม่บวกซ้ำ
- จะแสดง “เงินพร้อมใช้” เป็นเงินสดลบเงินกันค่าจ้างได้ต่อเมื่อโค้ดยืนยันว่ามีความหมายนี้ หากไม่ยืนยันให้แสดงสองค่าแยกกัน
- กำไรเป็นผลของรายรับรายจ่ายตามนิยาม engine ไม่เท่ากับการเปลี่ยนเงินสด และไม่ใช้เงินสดปลายงวดลบต้นงวดแทนกำไรโดยไม่ตรวจนิยาม
- ห้ามแสดงอัตราค่าจ้างเฉลี่ยจากยอดเงินกันค่าจ้างหารจำนวนคนงาน หากไม่มีหลักฐานว่าช่วงเวลาและฐานการนับตรงกัน
- การรวมเงินทุกภาคส่วนทำได้ในฐานะ “ยอดเงินสดรวมที่ติดตาม” เท่านั้น ไม่เรียกว่า GDP รายได้ ความมั่งคั่ง หรือกำไรของเมือง
- ห้ามใช้สมการเงินเข้าเท่ากับเงินออกเป็นข้อบังคับทดสอบ จนกว่าจะยืนยันแหล่งสร้าง/ทำลายเงินและขอบเขตระบบครบ

กราฟเวลาใช้ snapshot ที่บันทึกจริง มีแกนเวลา หน่วย และช่องว่างเมื่อไม่มีข้อมูล หากมีเพียงค่าปัจจุบัน ให้แสดงตัวเลขและข้อความ “ยังไม่มีประวัติสำหรับกราฟ” ไม่สร้างย้อนหลัง ไม่ทำเส้นแนวโน้มสุ่ม และไม่ต่อช่วงก่อนโหลดกับหลังโหลดโดยไม่ระบุ session หากเพิ่ม history ภายหลังต้องมีขนาดจำกัด schema version และการย้าย save ที่ตรวจแล้ว

## 7 การจัดวางหลายขนาดหน้าจอ

ใช้ขนาดพื้นที่แสดงจริงและรูปแบบการกดเป็นเกณฑ์ ไม่อิงชื่ออุปกรณ์อย่างเดียว ค่าต่อไปนี้เป็นเป้าหมายออกแบบที่ต้องปรับจากการทดสอบ ไม่ใช่ขนาดที่ยืนยันว่าเหมาะกับทุกเครื่อง

เดสก์ท็อปกว้างตั้งแต่ประมาณ 1,200 CSS pixels: HUD สูงประมาณ 56 ถึง 64 pixels แถบเครื่องมือล่าง 64 ถึง 80 pixels แผงตรวจอาคารขวา 320 ถึง 380 pixels แดชบอร์ดใช้พื้นที่ไม่เกินประมาณ 90% ของ viewport พร้อมขอบว่างและความสูงจำกัดให้เลื่อนภายในได้

จอกลางประมาณ 768 ถึง 1,199 pixels: ลด HUD เหลือข้อมูลสำคัญ 3 ค่า จัดแดชบอร์ดเป็นสองคอลัมน์ และอนุญาตให้แผงตรวจอาคารเป็น overlay ที่ไม่บีบแผนที่เล็กเกินไป คำอธิบายยาวย้ายลงรายละเอียด ไม่ลดขนาดอักษรเพื่อให้ทุกอย่างอยู่แถวเดียว

โทรศัพท์แนวตั้ง: HUD ใช้สองแถวสั้น แถบล่างแสดงเครื่องมือหลักกับปุ่ม “เพิ่มเติม” แผงตรวจอาคารเป็น bottom sheet ที่เปิดครึ่งจอหรือขยายเต็มได้ มีปุ่มกดขยาย/ย่อแทนการพึ่ง gesture อย่างเดียว แดชบอร์ดเป็นหน้าเต็มและใช้แท็บแนวนอนหรือรายการหัวข้อ ไม่ย่อคอลัมน์เดสก์ท็อปทั้งหมดลงในจอแคบ

โทรศัพท์แนวนอน: ให้ความสำคัญกับความสูงที่จำกัด ใช้ header แถวเดียว แผงรายละเอียดด้านข้างและเนื้อหาเลื่อน แถบล่างเตี้ยลงได้แต่พื้นที่กดต้องไม่เล็กลงจนใช้ยาก ปุ่มปิดและปุ่มยกเลิกเครื่องมือห้ามถูก browser bar บัง

โหมดเว็บไซต์เดสก์ท็อปบนโทรศัพท์: ทดสอบทั้ง layout viewport ที่กว้างขึ้นและ visual viewport ที่เห็นจริง รวมถึง browser zoom ไม่ถือว่า viewport กว้างแปลว่ามีเมาส์ ใช้เงื่อนไข coarse pointer เพื่อคงปุ่มขนาดสัมผัส ไม่ห้าม pinch zoom และไม่บังคับให้ผู้ใช้เปิดโหมดนี้เพื่อใช้งานเกม

ทุกขนาดต้องเผื่อ safe area ของรอยบากและแถบ home ใช้ความสูง viewport ที่ตอบสนองต่อแถบเบราว์เซอร์ หลีกเลี่ยง scroll ซ้อนหลายระดับ และรักษาพิกัดกล้อง รายการที่เลือก แท็บ และตำแหน่งเลื่อนเมื่อหมุนหน้าจอ

## 8 ภาษาภาพและการเข้าถึง

แนะนำธีมเมืองร่วมสมัยที่อ่านง่ายก่อน ไม่จำเป็นต้องเปลี่ยนโลกเกมเป็นยุคกลางตามภาพแรก ใช้แผงสีเข้มเกือบทึบ ตัวอักษรสว่าง และเส้นขอบอ่อนเพื่อแยกข้อมูล โดยค่าตัวอย่างสำหรับเริ่มออกแบบคือพื้นแผง #18232B, พื้นรอง #24343E, ข้อความ #F4F7F9, ข้อความรอง #BAC7D0 และสีเลือก #68C5FF ต้องตรวจ contrast บนพื้นหลังที่ประกอบจริงก่อนรับรอง

ใช้ spacing scale 4/8/12/16/24/32 pixels, มุมโค้ง 8 ถึง 12 pixels และเงาเพียงเล็กน้อยเพื่อไม่แข่งกับเมือง ตัวอักษรไทยเนื้อหาเริ่มที่ประมาณ 16 pixels หัวข้อ 20 ถึง 24 pixels line-height รองรับสระและวรรณยุกต์ ตัวเลขใช้ tabular numerals หากฟอนต์รองรับ ไม่ตัดบรรทัดไทยด้วยการใส่ช่องว่างผิดภาษา

ไอคอนควรเป็นชุดเดียวกัน ใช้ผลงานที่สร้างเองหรือชุดที่ตรวจใบอนุญาตแล้ว บันทึกแหล่งที่มา รุ่น และ attribution ตามข้อกำหนดในโครงการ ห้ามตัดไอคอนจากภาพอ้างอิงมาใช้หรือถือว่าภาพที่ผู้ใช้ส่งให้อนุญาตให้แจกจ่าย assets ต้นฉบับได้

ข้อกำหนดการใช้งาน

- ปุ่มสัมผัสตั้งเป้าอย่างน้อย 44 × 44 CSS pixels พร้อมระยะห่าง และมีชื่อที่อ่านได้ด้วยโปรแกรมอ่านหน้าจอ
- ใช้ keyboard เข้าถึง HUD เมนู รายการ และปุ่มย้อนกลับได้ ลำดับ Tab สอดคล้องภาพ และมี focus ring ชัดเจน
- หน้าต่าง modal จำกัด focus อยู่ภายในและคืน focus ให้ปุ่มเดิมเมื่อปิด แผง nonmodal ไม่ควรขัง keyboard
- ปุ่ม Escape ปิดเฉพาะชั้นบนสุดหรือยกเลิกเครื่องมือ ไม่สั่งสองอย่างพร้อมกัน
- Tooltip เปิดได้ด้วย focus/แตะ ไม่จำเป็นต้อง hover มีคำอธิบายข้อความสำหรับเครื่องหมายเตือนและสี RCI
- ใช้สีร่วมกับชื่อ/ไอคอน ไม่ใช้แดงเขียวล้วนบอกผลบวกผลลบ ลด animation เมื่อผู้ใช้เปิด reduced motion
- Screen reader ไม่ประกาศทุก tick ให้ประกาศเฉพาะการเปลี่ยนหน้าหรือเหตุการณ์สำคัญด้วยความถี่เหมาะสม
- แยกข้อความเป็น localization keys ใช้รูปแบบตัวเลขตามภาษา แสดงหน่วยและช่วงเวลาครบ และทดสอบข้อความภาษาอังกฤษที่ยาวกว่าพื้นที่เดิม

## 9 สถาปัตยกรรม GUI ที่ไม่ปนกับ simulation

แบ่งเป็น Game HUD, Tool Dock, Context Inspector, City Dashboard, Metric Card, Entity List, Data State, Dialog และ Navigation Controller ใช้ design tokens ร่วมกันและ adapter เดียวในการอ่านข้อมูล ไม่คัดลอกสูตรเดียวกันไปคำนวณในหลายหน้า

simulation เป็นเจ้าของเงิน งาน สินค้า และเวลาของเกม GUI เป็นเจ้าของแท็บที่เปิด การเลือกเครื่องมือ การเลื่อนรายการและ focus ส่วนคำสั่งก่อสร้างและเปลี่ยนสถานะเกมส่งผ่าน command ที่มีอยู่แล้ว การเปิดสถิติ การเรียงตาราง หรือเปลี่ยนภาษาต้องไม่เปลี่ยนผลจำลอง

ให้ทบทวนระบบ UI เดิมก่อนเลือกเทคโนโลยี หากใช้ DOM อยู่แล้วควรต่อยอด DOM overlay สำหรับตารางและข้อมูลที่ต้องเข้าถึงด้วย keyboard โดยไม่เพิ่ม framework ใหญ่เพียงเพื่อทำการ์ด ถ้าเดิมเป็น PlayCanvas UI ให้กำหนดขอบเขตและตัวจัดการ input ระหว่าง canvas/DOM ชัดเจน ไม่ย้ายทั้งระบบในรุ่นแรก

อัปเดตตัวเลขตาม snapshot หรือ event ที่มีอยู่ ไม่สร้างรายการทั้งหมดใหม่ทุก render frame ขณะเลือกบ้านและเดือนเปลี่ยนต้องอ่านชุดข้อมูลสอดคล้องกัน เมื่อปิดแผงให้หยุด subscription ที่ไม่จำเป็น และป้องกัน handler ซ้ำหลังเปิดปิดหลายครั้ง ข้อมูลส่วนตัวของ GUI ไม่ควรแก้ schema ของ save เกมโดยไม่จำเป็น

## 10 ลำดับพัฒนาและเงื่อนไขผ่าน

### ระยะศูนย์ ตรวจฐานเดิมและล็อกความหมายข้อมูล

รอรวมงานเมนูย่อยที่กำลังทำก่อนสร้าง dependency กับไฟล์เดียวกัน ตรวจ diff และจุดเชื่อม navigation เก็บภาพหน้าจอเดิมใน viewport ตัวแทน จัดทำ metric dictionary ระบุ field หน่วย ช่วงเวลา นิยามค่า 0 และ null ตรวจรายงานทดสอบเดิมอีกครั้งก่อนใช้เป็นฐาน จำนวนชุดทดสอบที่รายงานระหว่างงานไม่ใช่ผลผ่านของ GUI ใหม่

ผ่านเมื่อทั้งห้าเมนูยังเปิดและย้อนกลับได้ คำเรียกครัวเรือน เงินสด กำไร สินค้า และเงินกันค่าจ้างตรงกับโค้ด และไม่มีระบบที่ยังไม่รองรับถูกนำมาออกแบบเป็นตัวเลขจริง

### ระยะหนึ่ง โครงหน้าจอและการนำทาง

ทำ HUD, Tool Dock, panel shell, tokens และ navigation โดยนำเนื้อหาเมนูเดิมมาเสียบ ไม่แก้ simulation จัดการ pointer ไม่ให้คลิกทะลุ ทดสอบการปิด เปิด ย้อนกลับ และหมุนหน้าจอ

ผ่านเมื่อวางถนน/โซนได้เหมือนเดิม ปุ่มทุกหน้ามีทางออก ไม่เกิด modal ซ้อนโดยไม่ตั้งใจ และการเปิดข้อมูลไม่เปลี่ยนเงินหรือความเร็วเกม

### ระยะสอง แผงรายละเอียดและภาพรวมข้อมูลจริง

ทำ context inspector บ้าน บริษัท ถนน และพื้นที่ว่าง ต่อ adapter และสถานะไม่มีข้อมูล สร้างแดชบอร์ดภาพรวมพร้อมลิงก์สู่ห้าเมนูเดิม รอบนี้ยังไม่ต้องมีกลไกบริการใหม่หรือกราฟย้อนหลัง

ผ่านเมื่อยอดของ HUD แผงอาคารและแดชบอร์ดตรงกันใน tick เดียว ทุกจำนวนมีหน่วยถูกต้อง การลบ/โหลดไม่ทิ้ง entity เก่า และไม่มี capacity หรือชื่อบุคคลที่สร้างขึ้นเพื่อเติมภาพ

### ระยะสาม ปรับมือถือและตรวจการเข้าถึง

ปรับ bottom sheet แท็บและ safe areas ตรวจ keyboard, screen reader, zoom, ภาษาไทย และข้อความยาว วัดผลบนเครื่องเดียวกันกับ baseline ก่อนและหลังเปลี่ยน GUI โดยแยกเวลาที่ใช้ใน simulation ออกจาก GUI ไม่อ้างว่าเร็วขึ้นจากความรู้สึกอย่างเดียว

ผ่านเมื่อไม่มีปุ่มสำคัญถูกบัง ไม่มีเนื้อหาหลุดกรอบหรือเลื่อนทั้งหน้าโดยไม่ตั้งใจ และทุกเส้นทางหลักทำได้โดยไม่ใช้ hover

### ระยะถัดไป ประวัติและระบบใหม่

เพิ่มกราฟเมื่อมี history จริงและตรวจ save migration แล้ว ระบบประชากรรายบุคคล ความจุบ้าน น้ำไฟ โรงเรียน โรงพยาบาล จราจรและสินค้าหลายชนิดต้องมี design แยก กติกาและข้อมูลของตนเอง จึงเปิดพื้นที่ใน GUI ตามลำดับ ไม่ถือว่าเป็นงานตกแต่งหน้าจอ

## 11 แผน QA และภาพหลักฐาน

สร้างสถานการณ์ทดสอบที่มีเมืองว่าง มีครัวเรือนแต่ไม่มีบริษัท มีบริษัทไม่มีคนงาน สินค้าเป็นศูนย์ เงินเป็นศูนย์หรือค่าติดลบที่ engine อนุญาต รายการจำนวนมาก รหัสอ้างอิงหาย และโหลด save รุ่นเดิม ห้ามใส่สถานะจำลองที่ engine ไม่อนุญาตแล้วนำไปสรุปว่าเป็นบั๊กของเกม

Unit tests ตรวจ mapping หน่วย แยก missing จาก zero การรวมยอดแบบไม่ซ้ำ เงินกันค่าจ้างที่ไม่ถูกบวกซ้ำ และการเรียงรายการ Integration tests ตรวจเดือนเปลี่ยนขณะเปิดแผง บันทึก/โหลดขณะมีสิ่งที่เลือก และการเปลี่ยนเครื่องมือระหว่างหน้าต่างเปิด Browser tests ตรวจห้าเมนูเดิมทุกเส้นทาง พร้อมงานก่อสร้างจริงหลังปิดแต่ละหน้า

ชุดภาพหน้าจอขั้นต่ำสำหรับรับงาน

- เดสก์ท็อป 1440 × 900: HUD/แถบล่าง แผงบ้าน แผงบริษัท และแดชบอร์ด
- จอขนาดกลาง 1024 × 768: แดชบอร์ดสองคอลัมน์และรายการข้อความยาว
- โทรศัพท์แนวตั้ง 390 × 844 และจอแคบ 360 × 640: bottom sheet และเมนูย่อยที่มีปุ่มย้อนกลับ
- โทรศัพท์แนวนอน 844 × 390: แผงตรวจอาคารไม่บังปุ่มหลัก
- โหมดเว็บไซต์เดสก์ท็อปบนมือถือจริง: บันทึกทั้ง layout/visual viewport, zoom และชนิด pointer ไม่แทนด้วยภาพ desktop ที่ย่อขนาด
- การขยายข้อความหรือ browser zoom 200%: เส้นทางหลักยังอ่านและใช้งานได้

ทุกภาพระบุ build, ขนาด viewport, สถานการณ์เกม และสถานะเดิน/หยุดเวลา ใช้ข้อมูลเมืองที่กำหนดซ้ำได้เพื่อเทียบก่อนหลัง ตรวจด้วยสายตาเรื่องข้อความไทย clipping, z-index, tooltip หลุดกรอบ และความชัดของสถานะเลือก ภาพ mockup ต้องติดป้ายว่าเป็นแบบร่าง ไม่ใช้แทนหลักฐานว่าฟีเจอร์ทำงานแล้ว

เกณฑ์ปล่อยรุ่นต้องผ่านทั้งข้อมูลถูกต้อง เมนูเดิมไม่เสีย เส้นทางหลักใช้ได้บนมือถือ และไม่มี console error ใหม่จาก GUI หากภาพสวยแต่ตัวเลขผิดหรือปุ่มวางถนนทำงานทะลุแผง ถือว่ายังไม่ผ่าน

## 12 ขอบเขตรุ่นแรกที่เสนอ

รุ่นแรกควรส่งมอบโครงสี่ชั้น HUD และแถบคำสั่งที่อ่านง่าย แผงรายละเอียดบ้าน/บริษัท/ถนน แดชบอร์ดเมืองจากข้อมูลปัจจุบัน การนำทางร่วมกับห้าเมนูเดิม สถานะข้อมูลครบ และรองรับโทรศัพท์ทั้งสองแนว พร้อมหลักฐาน QA

ยังไม่รวมระบบน้ำไฟ บริการสังคม ความจุบ้านจริง บุคคลรายคน สินค้าหลายชนิด กราฟที่ไม่มี history การเปลี่ยนกติกาค่าแรง และการเปลี่ยนภาพโลกเกมเป็นยุคกลาง ขอบเขตนี้ทำให้ได้โครงสร้างแบบภาพอ้างอิงโดยยังซื่อสัตย์ต่อ CityManager ที่เล่นได้จริง และลดโอกาสที่การปรับหน้าตาจะทำให้ระบบเศรษฐกิจเดิมเสีย

ขั้นถัดไปก่อนเริ่มเขียนโค้ดคือยืนยัน wireframe ของหน้าหลัก แผงบ้าน แผงบริษัท และแดชบอร์ดในเดสก์ท็อปกับมือถือ แล้วล็อก metric dictionary และจุดเชื่อมเมนูเดิม จึงลงมือทีละระยะตามเกณฑ์ผ่านด้านบน
