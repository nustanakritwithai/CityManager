# แรงงานตามความสามารถของสมาชิกครัวเรือน

> ส่วนแรกบันทึกกติกาต้นทางรุ่น `worker-1`; สัญญาการสรุปสถานะที่รวมการศึกษาและงานสวนอยู่ใน [สรุปสถานะระยะ A](#สรุปสถานะระยะ-a-อ่านอย่างเดียว) ด้านล่าง ระยะ A ยังไม่เปลี่ยน UI หรือตัวจัดสรรงานเดิม

เอกสารนี้อธิบายกติกาเกมที่เสนอและนำมาใช้ในข้อมูลรุ่น `3 / worker-1` ไม่ใช่สูตรหรือข้อมูลสมดุลจาก Cities: Skylines II การจำลองยังใช้ครัวเรือนและสถานประกอบการแต่ละแห่ง ไม่มีตัวละครหรือการตัดสินใจรายบุคคล

## ปัญหาที่แก้

รุ่น `2 / household-1` นับแรงงานเป็นจำนวนคนอยู่แล้ว ผู้พึ่งพิงไม่ได้ถูกส่งไปทำงาน และหนึ่งครัวเรือนมีรายการจัดสรรได้หลายกิจการ แต่ตัวจับคู่งานเติมแรงงานที่เหลือของบ้านให้กิจการแรกตาม ID จนครบ แล้วรักษางานเดิมในวันถัดไป ถ้าบ้านมีแรงงานสองคนกับโรงงานที่มีสองตำแหน่ง ทั้งสองคนจึงมักอยู่โรงงานเดียวกัน แม้ภายหลังจะมีร้านค้าที่รับคนได้ นอกจากนี้ข้อมูลเดิมไม่มีทักษะของสมาชิกจริง มีเพียงอาชีพและตำแหน่งระดับเริ่มต้นในรายการจ้างงาน

การแก้ครั้งนี้เพิ่มกลุ่มความสามารถที่เป็นจำนวนคน และกระจายแรงงานส่วนเกินไปยังนายจ้างอื่นที่รับได้จริง แถวที่รวมข้อมูลตามครัวเรือนเป็นเพียงวิธีแสดงบัญชีร่วม ไม่ได้หมายความว่ากิจการจ้างสมาชิกทั้งครอบครัว

## ข้อมูลแรงงาน

`workerSkills` มีสามจำนวนที่ไม่ทับซ้อนกัน ผลรวมต้องเท่ากับ `workforce` ของบ้านนั้น:

| กลุ่มความสามารถ | งานที่รับได้ | ข้อจำกัดปัจจุบัน |
| --- | --- | --- |
| `general` — ทั่วไป | งานผลิตหรือค้าปลีกระดับเริ่มต้น | คนหนึ่งถูกจัดสรรได้เพียงครั้งเดียว |
| `manufacturing` — งานผลิต | โรงงานอุตสาหกรรม | ยังไม่มีประวัติการศึกษา/ประสบการณ์ |
| `retail` — ค้าปลีก | ร้านค้า | ยังไม่มีระบบฝึกทักษะ/เลื่อนตำแหน่ง |

กลุ่มเหล่านี้เป็นความสามารถหลักที่ไม่ซ้ำคน ไม่ใช่สามใบรับรองที่นับสมาชิกคนเดิมซ้ำหลายรอบ `members = workforce + dependents` และผู้พึ่งพิงไม่มีรายการจ้างงาน

แต่ละรายการจัดสรรระบุ `householdId`, `firmId`, `skill`, `occupation`, `rank` และ `workers` จึงแยกได้ว่ากิจการได้รับแรงงานกลุ่มใดกี่คนจากบ้านใด `rank` ยังมีเฉพาะ `entry` ไม่ได้อ้างว่ามีระดับอาชีพที่จำลองไว้แล้ว

เซฟ v1/v2 ไม่มีข้อมูลความสามารถเดิม การนำเข้าจึงกำหนดแรงงานเดิมเป็น `general` ทั้งหมด พร้อม `skillSource: legacy-assumed` อย่างเปิดเผย นี่เป็นสมมติฐานความเข้ากันได้ ไม่ใช่การค้นพบประวัติสมาชิก การโหลดไม่ย้ายงาน ไม่เดินเวลา และไม่สร้างค่าจ้างหรือเงินใหม่ การจัดสรรใหม่เกิดใน daily tick ถัดไป

ครัวเรือนเข้าเมืองใหม่แบบแรงงานเดี่ยวใช้กลุ่มทั่วไป ส่วนครอบครัวสองแรงงานใช้หนึ่งกลุ่มทั่วไปกับหนึ่งกลุ่มเฉพาะงานตามตำแหน่งที่มีงบรับจริง ณ การเข้าเมือง และแสดง `skillSource: arrival-profile` ตัวเลขและองค์ประกอบนี้เป็นการออกแบบเกมที่มีขอบเขต ยังไม่มีอายุ การเกิด การตาย หรือเส้นทางอาชีพรายบุคคล

## การจับคู่งาน

1. ตรวจจำนวนเต็ม กลุ่มความสามารถ และความสามารถเข้าถึงถนน รับได้ไม่เกินทั้งความจุและจำนวนตำแหน่งที่สำรองค่าจ้างได้
2. จัดกลุ่มเฉพาะงานผลิตและค้าปลีกก่อนกลุ่มทั่วไป โดยรักษางานเดิมที่ตรงกลุ่มแล้วเติมตำแหน่งตาม ID ที่เรียงแน่นอน วิธีนี้ไม่ปล่อยผู้มีงานที่รับได้เพียงประเภทเดียวว่างงานเพราะแรงงานทั่วไปครองตำแหน่งนั้นอยู่
3. จัดกลุ่มทั่วไปลงในตำแหน่งที่เหลือ กลุ่มทั่วไปอาจย้ายประเภทงานเพื่อเปิดตำแหน่งให้กลุ่มเฉพาะที่รับงานอื่นไม่ได้
4. เมื่อมีนายจ้างใหม่ที่ยังมีตำแหน่งและเงินรับจริง จึงย้ายส่วนเกินที่มีความสามารถตรงกันจากนายจ้างเดิม โดยยังเหลือแรงงานของบ้านนั้นอย่างน้อยหนึ่งคนที่นายจ้างต้นทาง ไม่ปลดแรงงานของบ้านอื่นเพียงเพื่อทำให้ภาพดูหลากหลาย
5. เป้าหมายส่วนแบ่งใช้จำนวนที่จ้างจริงหารจำนวนกิจการเดิมรวมเป้าหมายใหม่ ปัดขึ้น และจำกัดด้วยตำแหน่งว่าง/แรงงานส่วนเกินที่เข้าเงื่อนไข จึงไม่รับประกันว่าทุกครัวเรือนมีนายจ้างเท่ากันหรือกระจายเท่ากัน

ถ้ามีนายจ้างที่เข้าเงื่อนไขเพียงแห่งเดียว หรือสมาชิกมีความสามารถเหมาะกับงานเดียว ทั้งสองแรงงานอาจทำงานกิจการเดียวกันได้อย่างถูกต้อง ห้ามสร้างตำแหน่งหรือย้ายผู้พึ่งพิงมาเติมเพื่อให้ได้ภาพหลายนายจ้าง

การคำนวณเรียงครัวเรือน กิจการ และกลุ่มความสามารถแบบคงที่ ผลลัพธ์ไม่ขึ้นกับลำดับ array ที่ส่งเข้า และการคำนวณซ้ำบนอินพุตเดิมต้องคงผลเดิม ใช้การคำนวณจำนวนรวม ไม่มี object แทนสมาชิกแต่ละคน แต่ยังมีการตรวจคู่ entity แบบมีขอบเขต จึงไม่ได้พิสูจน์การรองรับประชากรหลักแสน–ล้าน

## เปลี่ยนอาชีพ (1.2)

ตอนชำระสิ้นเดือน แรงงานเฉพาะทาง (งานผลิตหรือค้าปลีก) ที่ว่างงาน ขณะที่สายของตัวเองไม่มีตำแหน่งว่างที่มีงบ แต่อีกสายมี จะเปลี่ยนเป็นแรงงานทั่วไป ไม่เกินจำนวนตำแหน่งว่างของอีกสาย (`retrainingMoves`) แล้วตัวจับคู่งานจัดให้ในวันถัดไป `skillSource` ยังเป็น `arrival-profile` เพราะยังเป็นครัวเรือนเดิม จำนวนในแต่ละกลุ่มยังรวมเท่ากับ workforce การย้ายออกของครัวเรือนที่ไม่มีงานดู [BALANCE.th.md](BALANCE.th.md#ประชากรและแรงงาน-12)

## เงินเดือนและการเลิกจ้าง

ยังใช้เงินจำนวนเต็มหน่วยสตางค์ หนึ่ง tick เท่ากับหนึ่งวัน จ่ายค่าจ้างทุก 30 วัน ตามอัตราเดิมของประเภทกิจการ บันทึกจำนวน worker-days และกันเงินจากกระเป๋ากิจการไว้จริง ค่าจ้างจากทุกนายจ้างเข้ากระเป๋าร่วมของครัวเรือนเดิม การเพิ่มกลุ่มความสามารถไม่ได้สร้างกระเป๋ารายบุคคลหรือเพิ่มค่าจ้างพิเศษ

การย้ายงาน การขาดการเชื่อมถนน การลดงบ หรือเลิกกิจการ ต้องไม่นับคนทำงานซ้ำ และต้องไม่ล้างสิทธิค่าจ้างที่ทำมาแล้ว ประวัติเงินและสินค้าเดิมยังต้องกระทบยอดได้ ไม่มีการเขียนประวัติใหม่เพื่อให้เข้ากับตำแหน่งงานปัจจุบัน

## เซฟเดิมและการกู้คืน

- เซฟใหม่เก็บใน `citymanager.save.v3` การอ่านปกติเลือก v3 ก่อน v2 แล้วจึง v1
- ไม่ลบหรือเขียนทับ `citymanager.save.v2` และ `citymanager.save.v1` มีปุ่มนำเข้าเดิมแยกตามรุ่น
- ตัวอ่าน v1/v2 ตรวจความถูกต้องด้วยกติกาเดิมก่อนแปลงข้อมูล ตัวอ่าน v2 แยกจากตัวจำลอง/ตัวจับคู่แรงงานใหม่ เพื่อไม่ใช้กติกาใหม่ไปซ่อมเซฟเก่าที่เสีย
- การโหลดไม่เขียน storage เมื่อบันทึกหลังนำเข้า จะสำรอง bytes เดิมก่อนเขียน v3 แต่ละรุ่นเก่ามีสำเนาไม่เปลี่ยนแปลงได้แปดช่อง (`citymanager.backup.v1` และ `citymanager.backup.v2` ตามด้วย `.1` ถึง `.7`) ข้อมูลเดิมที่ซ้ำใช้สำเนาเดิม ไม่สร้างสำเนาซ้ำ
- `citymanager.backup.latest` เป็นตัวชี้ชื่อช่องที่สำรองล่าสุด เพื่อให้กู้คืนล่าสุดได้ตรงแม้สลับนำเข้า v1/v2 ไม่ใช่สำเนาเซฟอีกชุด
- ถ้าสำรองเต็ม เขียน backup ไม่ได้ เขียนตัวชี้ไม่ได้ หรือเขียน v3 ไม่ได้ จะยกเลิกก่อนเขียนทับ primary ที่ยังดี หากสำรองสำเร็จแล้วแต่ primary ล้มเหลว สำเนานั้นยังใช้กู้คืนได้
- ถ้าเซฟที่ถูกเลือกเสีย จะรายงานข้อผิดพลาด ไม่แอบโหลดอีกเมืองมาแทน ผู้เล่นเลือกนำเข้า v1/v2 หรือกู้ backup ได้อย่างชัดเจน

## สรุปสถานะระยะ A: อ่านอย่างเดียว

`src/workforce-summary.ts` เพิ่ม `deriveWorkforceSummary(city)` เป็น snapshot จาก **จำนวนรวมของครัวเรือนที่มีอยู่จริง** ไม่ใช่ทะเบียนบุคคล ระบบเศรษฐกิจและการศึกษาเดิมยังเป็นเจ้าของข้อมูล มีเพียงโมดูลนี้และเทสต์ที่ใช้ API ใหม่ในระยะ A; panel, HUD, คำตอบเมือง, กราฟ, gate และสวนยังไม่ได้เปลี่ยนมาใช้ snapshot นี้

### สัญญาการนับ

- `population = workforce + dependents`
- `economicWorkers = employeeWorkers + ownerWorkers`
- `studying = schoolStudents + universityStudents`
- `occupiedWorkforce = economicWorkers + studying`
- `unassignedWorkforce = workforce - occupiedWorkforce`
- ดังนั้น `population = economicWorkers + studying + unassignedWorkforce + dependents`
- `unassignedShare = unassignedWorkforce / (economicWorkers + unassignedWorkforce)`; เป็น `null` เมื่อไม่มีตัวหาร หรือ snapshot ไม่ผ่าน reconciliation

ใช้คำไทยว่า **ทำงาน / กำลังศึกษา / ยังไม่ได้รับจัดสรรงาน / ผู้พึ่งพิง** สำหรับสถานะหลักที่ไม่ทับกัน `unassignedShare` เป็นสัดส่วนการจัดสรรในเกม ไม่ใช่อัตราว่างงานตามนิยามตลาดแรงงาน เพราะไม่มีข้อมูลอายุ ความตั้งใจหางาน หรือความสมัครใจทำงาน สัดส่วนนี้ไม่รับรองว่าคนที่ยังไม่ได้งานรับงานได้ทุกประเภท

`economicWorkers` รวมลูกจ้างฟาร์ม โรงงาน ร้านค้า เจ้าของที่มี `ownerLabor` พนักงานสวน ครู และอาจารย์ ผู้ที่ยังลงทะเบียนเรียนอยู่เป็น `studying` แม้การเรียนพักหรือรอที่สอน; snapshot อ่านบทบาทที่บันทึกไว้ ไม่เดิน tick หรือคาดเดาการเข้าเรียนวันนี้

อาชีพแยกจากสถานะหลักและทักษะ: `agriculture`, `manufacturing`, `retail`, `market-trading`, `park-maintenance`, `teacher`, `professor` โดยฟาร์มดู `Firm.zone === 'F'` แม้ allocation เดิมใช้ occupation `manufacturing` เหมือนโรงงาน `relationship` แยก `employee`, `owner-worker`, `student`; ผู้เรียนมีบทบาท `school-student` / `university-student` แต่ไม่เพิ่มยอดอาชีพทำงาน

`ownedFirmIds` คือกิจการที่ **ครัวเรือน** ถือครอง ไม่ใช่จำนวนเจ้าของรายบุคคล การมี ownership อย่างเดียวไม่เพิ่ม `economicWorkers` และไม่มีการสร้างค่าจ้างเจ้าของ ครัวเรือนที่ลงแรงเองหนึ่งคนและส่งสมาชิกอีกหนึ่งคนเป็นลูกจ้างจะนับสองหน่วยแรงงาน ไม่ใช่สามคนเพราะมี ownership เพิ่มด้วย

`skills` คัดลอกจำนวน `general / manufacturing / retail` ที่ยังรวมเท่ากับ workforce; `credentials.basic / higher` เป็นอีกแกน และ higher รวมอยู่ใน basic แล้ว ไม่บวกวุฒิเข้าประชากร ไม่มีข้อมูลจับคู่วุฒิกับทักษะรายบุคคล จึงไม่ใส่ `skill` ให้ assignment ครู/อาจารย์/ผู้เรียน ไม่ใช้ snapshot เปลี่ยนทักษะ ล้างวุฒิ หรือแทนการจัดสรรวุฒิให้ gate ของ #97

### ดัชนีและกำลังจากภายนอก

- `byHousehold.get(householdId)` ให้ counts, skills, credentials, ownership และ assignment rows ที่คัดลอกแล้ว
- `byWorkplace.get('firm:<id>' | 'park:<id>' | 'campus:<id>')` ให้ `localWorkers`, `learners`, `externalTeachers`, `externalProfessors` และ assignment rows
- `externalEducators` รวม `campus.contract` แยกครู/อาจารย์ภายนอก ไม่เพิ่มประชากร workforce หรือตัวหารสัดส่วนชาวเมือง
- ผลรวม localWorkers และ learners ของสถานที่ต้องตรง economicWorkers และ studying ของครัวเรือนเมื่อ snapshot ผ่าน reconciliation
- ไม่สร้างคนงานสาธารณูปโภค ขนส่ง หรือก่อสร้างจากความจุโรงไฟฟ้า ภาพรถ หรือยอดเงินบัญชี `construction` เพราะยังไม่มี allocation อาชีพเหล่านั้น

### ข้อมูลผิดและขอบเขต validation

ตรวจ `reconciled` และ `issues` ก่อนใช้ผลเป็นข้อเท็จจริง หากทำงาน+เรียนเกิน workforce จะคง `unassignedWorkforce` ติดลบให้เห็นและรายงาน `workforce-overallocated` ไม่ clamp หรือย้ายคนออกเพื่อให้ยอดดูถูกต้อง ตรวจยอดประชากร ทักษะเกินโควตา วุฒิที่ขัดกัน cohort ซ้ำ และ reference ที่หายด้วย ข้อมูลจำนวนที่ไม่ใช่จำนวนเต็มไม่ติดลบหรือ reference ที่หายจะมี issue; แถวนั้นไม่สามารถนำมาจัดกลุ่มได้ จึงไม่ควรใช้ totals ของ snapshot ที่ invalid เป็นยอดสมบูรณ์

นี่เป็น reconciliation สำหรับ **City ที่ผ่านการโหลด/ตรวจสอบตามสัญญาเดิมแล้ว** ไม่ใช่ตัว deserialize หรือ validator เซฟใหม่ และไม่ตรวจทุกกติกางบ กำลังผลิต ลำดับจัดสรร การเชื่อมถนน หรือประวัติการศึกษา การจ่ายค่าจ้างจริง/ค้างรับยังดู ledger และ workDays เดิม การเปลี่ยนสถานะไม่ล้างสิทธิที่ทำมาแล้ว

### ความบริสุทธิ์ ประสิทธิภาพ และเรื่องที่ยังไม่อนุมัติ

อ่านหนึ่งรอบตามจำนวนครัวเรือน สถานประกอบการ และ allocation/cohort rows; ไม่วนตามจำนวนสมาชิก ไม่ใช้ RNG ไม่ scan ledger ไม่เรียก serialize ไม่เดินเกม และไม่เพิ่ม cache ที่อาจค้างเมื่อแก้ข้อมูลภายใน tick เดียว ผลลัพธ์ไม่อ้าง mutable objects ของ City (ReadonlyMap/readonly เป็นสัญญาระดับ TypeScript ไม่ใช่ runtime freeze)

ผู้ใช้ API ควรเรียกเมื่อ state/revision ที่เกี่ยวข้องเปลี่ยน ไม่เรียกทุก animation frame การต่อ cache/revision เข้ากับ consumer เป็นงานระยะ B; เทสต์ cohort ใหญ่ยืนยันเพียงว่าไม่แตกหนึ่ง object ต่อคน **ไม่ใช่ผล benchmark รองรับเมืองล้านคนบนมือถือ**

ระยะ A ไม่เปลี่ยน `householdWorkerCount`, allocator, เงิน/RNG, schema/bytes ของ save, ลำดับ gate, ระดับอาคารเดิม, เวลาเกม หรือ park member-slot roster เซฟไม่มี education ให้สรุปบทบาท/วุฒิเป็นศูนย์โดยไม่เพิ่ม education field หรือแจกวุฒิ

ยังต้องตัดสินใจก่อนระยะ B: บ้านที่มีแต่ผู้เรียนจะผ่าน working-household gate หรือไม่; ปิดสถานศึกษาจะคง enrollment reservation หรือปล่อยรับงาน; ownership ที่ไม่ลงแรงจะยังกันโควตาเข้าเรียนหนึ่งคนหรือไม่ ส่วนเรียนควบงาน/part-time และอาชีพใหม่ต้องมีระบบรองรับก่อน ไม่ใช่เพิ่ม label หรือบวกคนซ้ำ
