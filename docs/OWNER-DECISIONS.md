# กฎตัดสินใจของเจ้าของตลาด รุ่นแรก

ชั้นนี้ใช้กฎในเครื่องเพื่อเสนอ **คงเดิม / เติมทุน / ถอนกำไร** ให้ตลาดที่มีครัวเรือนเจ้าของจริง ใช้ข้อมูลจาก simulation ปัจจุบัน ตรวจซ้ำก่อนเรียกคำสั่งเดิม และเก็บหลักฐานสำหรับ replay ยังไม่มีการเรียก Typhoon หรือคำสั่ง `decision-proposal` ฝั่ง API

## โหมดที่ทำงานจริง

| โหมด | พฤติกรรม |
|---|---|
| ปิด | จำลองเมืองตามเดิม ไม่มีการประเมินหรือทำรายการจากกฎ |
| รับข้อเสนอ | ค่าเริ่มต้น ประเมินหลังจบวันที่หารด้วย 30 ลงตัว หรือเมื่อผู้เล่นกดประเมิน ผู้เล่นเลือกทำรายการเอง |
| กฎทำรายการเอง | ผู้เล่นเปิดชัดเจนในเมืองที่เปิดอยู่ ประเมินและทำรายการเดือนละครั้ง เรียงตามรหัสตลาด |

โหลดเซฟหรือเริ่มใหม่กลับโหมดรับข้อเสนอเสมอ ไม่มีการคืนค่า auto จากเซฟหรือไฟล์ replay ตลาดที่ไม่มีข้อมูลพอให้คงเดิม ข้อเสนอที่เก่า เปลี่ยน actor จำนวนเงิน หรือรหัสอ้างอิงจะไม่ผ่านการตรวจซ้ำ ข้อเสนอเดิมทำซ้ำไม่ได้ใน session

## เงินที่กฎกันไว้

- เงินทั้งหมดเป็นจำนวนเต็มสตางค์
- กันเงินครัวเรือนสำหรับอาหารหนึ่งตะกร้าต่อครัวเรือนต่อวัน 30 วัน ตามกติกาปัจจุบัน 800 สตางค์ต่อวัน และค่าเช่าบ้าน 10,000 สตางค์ รวม 34,000 สตางค์ ไม่คูณตะกร้าตามจำนวนสมาชิก
- กันเงินตลาดสำหรับค่าจ้างที่เกิดขึ้นแล้ว ภาษี ค่าเช่ารอบหน้า และเงินหมุนเวียนขั้นต่ำ 20,000 สตางค์
- เติมทุนจากเงินครัวเรือนที่เหลือเหนือเงินจำเป็นเท่านั้น ถอนเฉพาะจำนวนที่ผ่านเกณฑ์กำไรของ `ownerFinance` และยังเหลือเงินกันไว้ของตลาด
- จำนวนต่อข้อเสนอไม่เกิน 10,000 สตางค์ เป็นพารามิเตอร์ของ `owner-rule-1` ไม่มีการสร้างเงิน สินค้า คน หรือทุนจากข้อเสนอ

เงินกันไว้เป็นนโยบายล่วงหน้าของต้นแบบ ไม่ใช่งบดุลครบถ้วน โรงงานและฟาร์มไม่มี household owner ในรุ่นนี้ `fundedBy` ของโรงงานยังเป็นที่มาทุนตาม `growth-1` ไม่มี `expandLevel` หรือ `setHiringTarget` เพิ่มเข้ามา

## Journal และ replay

Canonical city/save ยังคง **v6 / growth-1** โดยไม่เพิ่มฟิลด์ decision ลงใน City ประวัติเป็น sidecar ของ session ผู้เล่นส่งออกไฟล์ได้จากแผงเจ้าของตลาด ไฟล์ประกอบมี snapshot เมืองสำหรับ replay ในเครื่อง

Journal เก็บ actor, policy/rules version, snapshot/state fingerprints, คำสั่งตามลำดับ ผล validation และผลทำรายการ ช่วง tick ที่ต่อเนื่องกันรวมได้ไม่เกิน 30 วัน ก่อนตัดสินใจจะจำลองช่วงนั้นซ้ำจาก boundary และเทียบสถานะจริง

ค่าเริ่มต้นเก็บ checkpoint หนึ่งชุดและหน้าต่างล่าสุดไม่เกิน 256 events พร้อมสรุปช่วงที่ retire ล่าสุด 8 ช่วง การหมุน checkpoint เปลี่ยนขอบเขตที่ replay ย้อนกลับได้อย่างชัดเจน ไม่อ้างว่ารักษาประวัติทั้งเกมตลอดไป ขนาด sidecar จำกัด 32 MiB หากเก็บหลักฐานไม่ได้ กฎพักการทำรายการและกลับโหมดเสนอ แต่ simulation เมืองยังเดินต่อได้

คำสั่งผู้เล่นต้องผ่าน `beforeExternal` แล้ว `syncExternal` เพื่อเริ่ม coverage ใหม่จากสถานะที่ยืนยันแล้ว การเปลี่ยน state ที่ไม่ได้แจ้งจะทำให้หลักฐานตรวจไม่ผ่าน การตรวจ replay ใช้สำเนาเมือง ไม่เขียนสถานะกลับเมืองที่กำลังเล่น Fingerprint ใช้เทียบความตรงกัน ไม่ใช่ลายเซ็นรับรองความถูกต้องจากเซิร์ฟเวอร์

ประวัติอยู่ในหน้าที่เปิดเมืองรอบนี้ ส่งออกก่อนโหลดหรือเริ่มใหม่ เซฟ v1–v5 ยังนำเข้าผ่าน migration เดิมโดยไม่เปิด auto

## หลักฐาน benchmark

ทดสอบ 720 วัน × seeds `61025`, `20261023`, `1`, `42` เปรียบเทียบ fixed `growth-1`, proposal-only และ rule execution ใช้ production retention 256 events รอบนี้ทุก seed เก็บ coverage วัน 0–720 ได้ครบ ไม่มี retired events

| Seed | คน / ครัวเรือน / งาน ของ baseline และ rule | ทำรายการ / คงเดิม |
|---|---|---|
| 61025 | 19 / 11 / 15 | 31 / 9 |
| 20261023 | 19 / 11 / 15 | 29 / 11 |
| 1 | 18 / 12 / 15 | 45 / 0 |
| 42 | 19 / 11 / 15 | 30 / 10 |

Proposal-only มี canonical state ตรงกับ baseline ทุก seed ตรวจสมดุลเงิน สินค้า พืชผล inventory และเงินสดภายในไม่ติดลบทุกวัน ตรวจ earned-wage reserves, save round-trip และ replay ตรงกัน ไม่มี provider call ผลนี้ยืนยันความสอดคล้องของระบบ ไม่ใช่หลักฐานว่ากฎเป็นนโยบายเศรษฐกิจที่ดีที่สุด รายงานสรุปพร้อม source hashes อยู่ใน [owner-decision-benchmark.json](owner-decision-benchmark.json)

ใช้ `npm run test:owner` สำหรับ policy/journal/benchmark และ `npm run test:owner:browser` หลัง build และเปิด preview ที่พอร์ต 4191 เพื่อทดสอบแผงจริงบน desktop และขนาด S22 ชุด browser ปิดทางเรียก API/provider ทุกเส้นทาง

LLM treatment ผ่าน interface เดียวกันเป็นงานระยะถัดไป ต้องมี operation และการตรวจข้อเสนอที่ review แล้วก่อนเปิดใช้ ไม่เปลี่ยนคำตอบจากกฎให้แสดงเป็นคำตอบของ Typhoon
