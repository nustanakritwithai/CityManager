# ส่งตรวจซ้ำ: race ของรหัสกู้คืน

ฐานงาน: `fe62a456a67fe8e2c1b663265755fb93fb16dfa1` บน `feat/thai-auth-ui` อ้างอิงข้อพบทีม 5 ใน `team5-review-th.md`, `team5-review-followup-th.md`, `review-findings.test.mjs` และ `review-adversarial.test.mjs` กรณีบัญชีเท่านั้น เอกสารนี้เป็น handoff เพื่อขอทีม 5 ตรวจซ้ำ ไม่ใช่การอนุมัติรวมงานหรือ deploy

**ต้นเหตุ:** ตัวล็อกเดิมแยกตาม action จึงเริ่ม prepare B ขณะ confirm A ค้างได้ เมื่อ confirm A กลับมา callback เคลียร์ `pendingRecovery` และรหัสบนจอโดยไม่ตรวจว่าเป็น A หรือไม่ ทำให้ผู้เล่นอาจเข้าใจผิดว่ารหัส B ได้รับการยืนยัน ทั้ง baseline และแพตช์เดิมมีความเสี่ยงนี้

**การแก้:** ใช้ตัวล็อกร่วมสำหรับ authorize, create, recover, prepare และ confirm พร้อมปิดปุ่มทั้งห้าระหว่าง request; confirm จับสำเนา request ID/รหัสที่แสดง และตรวจ object กับ session generation ก่อนเคลียร์หรือแจ้งสำเร็จ; prepare ตรวจ generation ก่อนแสดงผล; การเปลี่ยน session ที่ผู้เล่นยืนยันแล้วจะล้างรหัสที่ยังรอยืนยันก่อนส่ง request แม้ response จะล้มเหลว เพราะผลจริงของ request อาจไม่แน่นอน ส่วนการยกเลิกสร้างบัญชียังเก็บรหัสเดิมไว้ ผล identity เก่าที่ตอบช้าถูกละเลยหลังเริ่มเปลี่ยน session เมื่อ handshake มาถึงระหว่าง action จะไม่เริ่ม authorize ซ้อน ผู้เล่นยังเลือกเข้าสู่บัญชีเองได้หลัง action จบ

**หลักฐาน:** ก่อนแก้ `node --test tests/pages-login-races.test.mjs` มี 4 fail, 1 pass; หลังแก้ `node --test tests/pages-login-races.test.mjs tests/pages-login-thai.test.mjs tests/pages-login-public-contract.test.mjs` ผ่าน 18/18 รวม A-confirm/B-prepare, prepare ค้างแล้ว confirm, การตอบกลับ stale ที่จำลองโดยตรง, ล็อกทุกคู่ action, cancel, prepare/confirm failure, session switch สำเร็จ/ล้มเหลว, delayed identity และ handshake ระหว่าง action ตรวจ Edge จำลองมือถือ 390×844 ด้วย endpoints ที่ intercept เป็น mock: รหัส A ยังแสดงและปุ่มทั้งห้าถูกปิดระหว่าง confirm; เมื่อ confirm สำเร็จจึงล้างรหัส ไม่มี horizontal overflow

**ข้อจำกัดสำหรับผู้ตรวจ:** ล็อกเป็นสถานะในหน้าต่างเดียว ไม่ใช่ lock ข้ามแท็บหรือการรับประกันผลคำขอที่ขาดการเชื่อมต่อ; backend และ recovery protocol เดิมไม่ได้เปลี่ยน และยังไม่ได้ทดสอบ backend จริงหรือ session ข้ามแท็บ ไม่มีการเปิดบัญชีจริงหรือใช้ credentials ภาพต้นฉบับถูกตรวจโดยทีมหลัก ไม่ได้ถูก materialize ใน executor นี้ ทีม 5 ควรตรวจ diff, กรณี cross-tab/network uncertainty และ contract ของ backend แยกก่อนตัดสินใจ ขั้นตอนสร้าง staged candidate และ baseline hash อยู่ใน README; staged file เป็น output ที่สร้างใหม่ได้ ไม่ใช่ production

## ตรวจต่อ: เครือข่ายและหลายแท็บ

แก้ต่อจาก `1c21cce31287543ebbc33212a9290c25397a0ea2`: หาก fetch หรือการอ่าน response ล้มเหลว หน้าจอแจ้งว่ายังไม่ทราบผล การยืนยันยังเก็บรหัสและ request ID เดิมไว้ให้ลองซ้ำ หากได้รับคำตอบแน่ชัด `recovery rotation superseded` หรือ `recovery preparation expired` จะล้างรหัสที่ยืนยันต่อไม่ได้และแนะนำให้สร้างใหม่ ข้อความหลังยืนยันแจ้งว่ารหัสอาจถูกแทนที่จากแท็บอื่น

**ผลตรวจโค้ดแบบอ่านอย่างเดียว:** สำเนา `market-server-release-6269011/src/pages-auth.js` ที่ตรวจมีการ lock แถวบัญชีระหว่าง prepare/confirm; confirm ตรวจ `previous_code_hash`, ตรวจ account/request ID และมีทางตอบสำเร็จซ้ำสำหรับคำขอที่ยืนยันแล้วเมื่อ active hash ยังตรง นี่เป็นการอ่าน source ไม่ใช่หลักฐาน PostgreSQL, การทำงานข้าม process หรือสถานะ production ปัจจุบัน การทดสอบสองแท็บใน `tests/pages-login-races.test.mjs` ใช้ model จำลองเงื่อนไขดังกล่าว ไม่ใช่ backend จริง

สำเนา source ที่นำมาสร้าง staged candidate มี SHA-256 `b7a4638df16bd01914444b1bcd6a71dbfc11093201c011b56f6e057afa89464f`; generator ตรวจ hash ของ HTML เดิมก่อนสร้างและไม่แก้ source การทดสอบใหม่สองกรณี network outcome และ superseded ล้มเหลวทั้งคู่ก่อนแก้ จากนั้น focused suite ทั้งสามไฟล์ผ่าน 23/23 รวม simulated commit ก่อน response หาย, response อ่านไม่ได้, expired, แท็บแข่งขันและข้อจำกัดที่แท็บเก่าไม่อัปเดต ตรวจ syntax ของ staged candidate ผ่าน

**ข้อจำกัดที่ยังเปิด:** ล็อกหน้าเว็บไม่ประสานแท็บอื่น ถ้าแท็บ B ยืนยันรหัสใหม่หลังแท็บ A สำเร็จ ข้อความเก่าที่ A ไม่อัปเดตอัตโนมัติและรหัส A อาจใช้ไม่ได้อีก; cookie/session เปลี่ยนจากอีกแท็บก็ไม่เพิ่ม `sessionGeneration` ในแท็บนี้ และยังไม่มีหลักฐานพิสูจน์ทุกลำดับผลตอบกลับ ในกรณี server อาจ commit แต่ response หาย การลองซ้ำใช้ request เดิมได้เฉพาะตราบใดที่หน้านี้ยังเก็บข้อมูลในหน่วยความจำ การปิด/รีโหลดทำให้ข้อมูล pending หายและ frontend ไม่สามารถตัดสินผลย้อนหลังได้จาก protocol นี้ ผู้เล่นต้องเก็บรหัสที่เห็นไว้ และต้องให้ทีม 5 ตรวจสถานะนี้และ backend contract โดยตรงก่อนพิจารณาใช้งานจริง **HOLD deploy** ไม่ถือว่าการจำลองสองแท็บหรือ frontend lock พิสูจน์ความปลอดภัย backend
